Roguelike Production Ecosystem System Design Document

High-Level Vision

The game is a run-based roguelike autobattler centered around emergent production ecosystems instead of deterministic crafting recipes.

The player does not directly craft items. Instead, they shape buildings, rooms, villagers, and tag pressures to influence what kinds of items are generated each week.

The core fantasy is:

Designing evolving industrial cultures that generate powerful and unpredictable combat builds.

The player gradually transforms buildings into specialized ecosystems such as:

disciplined military foundries

unstable arcane laboratories

lightweight evasive leather workshops

cursed occult industries

tempo-oriented mobility studios

The gameplay is about:

shaping probabilities

crossing specialization thresholds

engineering synergistic production pipelines

adapting to generated opportunities

creating emergent item identities

The system is intentionally:

probabilistic instead of deterministic

systemic instead of recipe-driven

compositional instead of hardcoded

run-based instead of permanent

Core Gameplay Loop

Weekly Loop

Player acquires villagers, rooms, and upgrades

Player assigns villagers to rooms

Buildings calculate total tag pressures

Rooms generate item opportunities

Modifiers and thresholds alter generation outcomes

Items are generated

Player equips teams

Battles occur

Rewards feed back into the ecosystem

Repeat

The player is not solving fixed recipes.

The player is shaping:

tendencies

environments

identities

specialization paths

Core Design Philosophy

Important Principle

The system should never devolve into:

Match tag color with room color.

Instead, the player should constantly make strategic decisions involving:

specialization

The goal is:

meaningful directional pressure rather than solved optimization.

ROOMS

Rooms should ask strategic questions.

Room Structure

Each room contains:

1. Element

Thematic environment.

Examples:

Fire

Water

Arcane

Nature

Wind

Earth

Elements are used by villager passives and interactions.

2. Base Effect

The room’s default effect.

Example:

Increase power

Increase perk count

Improve stability

Reduce weight

3. Scaling Rule

The room scales using tag pressure.

Example:

Gain power scaling on Metal

Gain perk chance scaling on Arcane

Scaling can be:

positive

negative

threshold-based

nonlinear

4. Tradeoff

Every room should contain meaningful downsides.

Examples:

More power but heavier

More perks but lower stats

More mutations but instability

More consistency but lower ceiling

5. Threshold Effects

Special breakpoints unlocked at certain tag values.

Example:

15 Fire → molten traits enabled

30 Arcane → extra perk slot

40 Martial → legendary weapon outcomes

Thresholds create:

specialization goals

nonlinear scaling

strategic commitment

Examples:

ITEM GENERATION PIPELINE

This is the core technical structure.

The game should use:

staged generation with modifier injection hooks.

Generation Pipeline Phases

1. Create generation context
2. Calculate tag pressures
3. Determine item category
4. Roll base item
5. Apply room modifiers
6. Apply villager modifiers
7. Apply threshold effects
8. Roll perks
9. Resolve mutations
10. Finalize item

Each phase emits hooks.

Modifiers subscribe to these hooks.

MODIFIER SYSTEM

The modifier system is the most important architecture layer.

Everything becomes modifiers:

rooms

villagers

events

relics

upgrades

corruption

weather

evolutions

Modifier Hooks

Use standardized lifecycle hooks.

Example:

enum ModifierHook {
	BEFORE_ITEM_GENERATION,
	AFTER_ITEM_GENERATION,
	BEFORE_PERK_ROLL,
	AFTER_PERK_ROLL,
	CALCULATE_TAG_PRESSURE,
	CALCULATE_WEIGHT
}

Modifiers register to hooks.

Example Modifier

class_name HeavyArmorModifier
extends Modifier

func applies(context) -> bool:
	return (
		context.room.element == "fire"
		and context.item.category == "armor"
	)

func execute(context):
	context.weights["heavy_armor"] += 25

GENERATION CONTEXT

A shared mutable object passed through the pipeline.

Purpose:

decouple systems

avoid parameter explosion

centralize simulation state

Example

class_name GenerationContext
extends RefCounted

var building
var room
var villagers
var item
var tags
var weights
var flags
var history

EVENT SYSTEM

Use an event bus.

Avoid direct dependencies.

Example

EventBus.emit("item_generated", context)

Systems listen independently.

This enables:

emergent mechanics

reactive systems

future scalability

WEIGHTED PROBABILITY SYSTEM

Do NOT directly manipulate percentages everywhere.

Instead:

use weighted pools

modifiers alter weights

final roll selects outcomes

Example

weights = {
	"heavy_armor": 10,
	"light_armor": 5
}

Modifiers adjust weights.

THRESHOLD SYSTEM

Thresholds should be generic data structures.

Example

class Threshold:
	var tag
	var value
	var effect

This allows rooms to define:

HISTORY SYSTEM

CRITICAL ENGINEERING PRINCIPLES

1. Composition Over Inheritance

Avoid:

Blacksmith.gd
Arcanist.gd
RunePriest.gd

Prefer:

VillagerData
+ tags
+ modifiers
+ methods

Behavior emerges from composition.

2. Systems Modify Context

Avoid:

villagers directly editing items

rooms directly editing perks

Everything modifies:

GenerationContext

This keeps systems modular.

3. Declarative Content

Prefer data-defined rules.

Avoid hardcoding.

Good:

Condition:
Fire >= 20

Effect:
Enable molten traits

Bad:

if fire > 20:
	enable_molten_traits()
